# 开发历史

十天（09-16 → 09-25）、71 个提交、28 条决策记录。

这份复盘按阶段梳理，重点不在"做了什么"，而在**转折点**和**代价最高的几个教训**
—— 后者才是下次能省下时间的东西。

规模：Python 10.8k 行 / SQF 23.9k 行 / C++ 1.3k 行，242 个测试。

## 一、P0 离线知识层（09-16）

从零建起 MCP 骨架、自带命令库（5181 条）、闸门分级、独立性自检（D1–D11）。

特征是**先把规矩定死**：

- 手写 JSON-RPC 而不依赖官方 SDK（D1）—— 运行时只用 Python 标准库；
- **硬禁命令不接受任何开关**（D2）：参数一旦能是任意字符串，白名单就退化成装饰；
- **失败必须响亮**（D10）：通道未接通时 `exec` 明确报错，绝不假装成功。

这一阶段的判断后来一次都没被推翻，成了所有后续工作的地基。

## 二、P1 通道：连续三次推翻自己的部署方案

MCP 与游戏分处 WSL / Windows 两侧，这一段几乎全程在跟"跨系统"较劲：

| 尝试 | 结果 |
|---|---|
| TCP 通道，MCP 做服务端 | ✅ 方向对了（D12，推翻了原"命名管道"设计） |
| 把 MCP 移到 Windows 侧 | ❌ **撤回**：WSL 里的 Node 无法执行 Windows 程序（D13 → D14） |
| 恢复 Windows 侧，改用 HTTP 传输 | ✅ 可行（D15） |
| 直连不通 → 怀疑代理、怀疑 Node | ❌ 全部猜错 |
| **真凶：Windows 防火墙** | ✅（D16） |

**代价最高的一课**：`curl` 会读 `HTTP_PROXY` 而 Node 的 `undici` 默认不读，于是
"curl 通了"被当成"网络可直连"，结论被带偏了整整一轮。另外**防火墙 DROP 表现为
超时而非拒绝**，与"路由不可达"难以区分 —— 越像网络问题的，越要先怀疑策略层。

## 三、P1 游戏侧：SQF 接口层的连环坑

真正上机之后，问题从"连不上"变成"发出去了没反应"，一个接一个：

- 4 处函数调用缺 `call`（引擎**加载期**才报错）；
- 字符串转义错了 **190 处**（SQF 的转义是两个连续引号，不是 C 的 `\"`）→ 改为让引擎自己序列化；
- **`poll` 必须用单字符串形式** —— 数组形式返回值是三元素数组，命令内容不在以为的位置，症状是"进了队列却永远取不到"；
- **`push` 同理**，数组形式导致上行完全不通；
- `params` 的类型约束把 HashMap 拒掉，cid 与结果被静默吞掉。

**共同特征**：两端日志都看不出问题。第 36 个提交（`1e44481`）链路首次闭环，
靠的是**先加诊断**（`game_link` 直接查 DLL 内部状态）而不是继续猜。

## 四、P2 输入与视觉

- 输入注入与截图起初被放进 DLL，**架构上错了**（走 SQF 转发），修正为 DLL 直连；
- 客户端**停在主菜单**时 `preInit/postInit` 不触发 → `-init=` 提前加载 DLL；
- **`-init=` 里的引号会被参数链吃掉**（`start` 命令、`execVM`、裸路径各踩一次）
  → 最终用 `toString [字符码]` 构造所有字符串，一个引号都不写；
- 第三方 provider 会丢弃工具返回的图片 → 打补丁把图片提升为带 text 的 user 消息
  （**纯图片消息会被网关丢弃**）。

## 五、真机联调（最近这一轮，44 个提交）

三个目标各自有了结局。

### 诊断链路（D17–D18）

`game_link` 本身是个排查工具，却因为 `status` 漏在 DLL 直连白名单外而**永远超时**
—— 要查不通的原因，得先用一个不通的工具。修法是把它挪进直连白名单，并加**执行器
心跳**（`poll_ms_ago`），让"TCP 已接通"不再冒充"有人在执行命令"。

### 主菜单启动执行器（D19–D20）：探明不可行

试了两版方案，最后用同步探针拿到确凿答案：**主菜单阶段模组 CfgFunctions 没有编译**，
且 `spawn` 在 `-init=` 阶段静默失效。这是引擎行为，不是写法问题 —— 记录在案，不再试。

### P2 坐标校准与 P3 无头形态（D21–D28）

- **`exec` / `config` 全链路真机闭环**；
- **P2**：`ui_locate` 把控件归一化坐标换算成可点坐标（离线的 `(680,407)` 与真机一致）；
- **P3**：专用服务器上判为无头、UI 工具明确拒绝，而 `exec` / `config` 照常可用。

## 贯穿全程的四类教训

**一、静默失败是主要敌人。** 至少六个 bug 的症状是"没反应"或"很慢"：漏 `call`、
转义错、`poll` 形式错、`status` 不在白名单、`configClasses` 少参数、失败回执缺引号。
它们的真相只在 RPT 的 SQF 堆栈或原始字节里。**遇"无响应"先翻堆栈，别先假设性能。**

**二、猜外部环境的事实必错。** 窗口类名（我猜 `ConsoleWindowClass`，实际是 `#32770`
对话框类）、`-autoInit` 的前提（要 `persistent = 1`）、任务搜索路径（`-profiles=`
并不改它）—— 三次都是"我以为我知道"。**先问环境，再写代码。**

**三、测试的假端比真端宽容，会掩盖真端的崩溃。** 契约测试的 handler 对 keys 做了
`isinstance` 容错，而真端直接抛异常，于是"参数位置错位"在测试里完全看不见。
所以新增了直接断言**负载形状**的测试，并**反向验证**过（把实现改回旧的，测试必须失败）。

**四、把判据写成具体数字。** "看它能不能跑"会放过"改了一半"的修复 —— 配额改造漏删
一个 `break`，改了配额却行为不变，直到真机上看到 `scanned` 仍是 40 才现形。
写成"期望是 80"之后，对不上时能立刻定位。

## 其他

- **`_x64` 副本的疏漏**：引擎优先加载 `arma3_mcp_x64.dll`，而 CMake 的后置复制在游戏
  运行时必然失败 —— 有一轮修好的 DLL **从未在游戏里生效过**，直到发现副本是旧的。
  现在校验脚本会比对两者 sha256。
- **协议层噪声**：`hello_ack` 被当成命令塞进 SQF 队列，每次连接都产生一条 cid 为空的
  假回执 —— 这也解释了此前反复出现的 `inbox=1`。
- **失败原因到不了 MCP**：`fn_sendAck` 把错误文本裸拼进 JSON 的 `error` 字段，缺了引号，
  整个回执不是合法 JSON，于是**所有失败原因都被丢弃**，调用方只能等超时。
