# 受限动态表达式方案（B 的落地形态）

本文件说明：为什么最终选了动态表达式、它被限制成什么样子、以及实测数据。
命令覆盖面会持续扩大，逐族生成静态分发的成本会反复支付，故采用动态表达式；
但**不是**把 `compile` 交给调用方，而是把它锁在"白名单命令 + 纯数据参数"里。

## 一、风险分析与分层对策

动态执行的实际风险不在 `compile` 本身，而在于**谁构造那段被编译的文本**。

在静态分发（`switch`）方案里，编译器免费提供了一条保证：**命令名在编译期就是
字面量**，无法被注入。改用动态表达式后，这条保证没有了——必须有人补上：

| 风险 | 对策 | 实现 |
|---|---|---|
| 命令名被注入（`_p0 evilCode _p1`） | **词法级白名单**：表达式里每个标识符必须是占位符或白名单命令 | `knowledge/expr.py` |
| 参数被当成代码 | 参数只经 `fromJSON` 成为**数据**，表达式里只出现 `_p0` 占位符——**永不拼接参数** | 同上 + SQF 侧 |
| 一条请求塞多语句、绕过计数审计 | 拒绝分号 | 同上 |
| 在表达式里夹带字符串形式的代码 | 拒绝字符串字面量 | 同上 |
| 表达式语法本身写错（静态方案由编译器挡） | 用**真实解析器**在交付前验证 | `tools/sqf_syntax_check.py` |
| 改全局状态（`setVariable`/`publicVariable*`） | 这些名字进 `DENY_NAMES`，即使命令库收录也不可触达 | `knowledge/expr.py` |

## 二、三层校验

```
第一层  MCP 侧（knowledge/expr.py）
        下发前词法校验：命令名白名单 + 占位符范围 + 无分号 + 无字符串
   ↓
第二层  SQF 侧（P1 落地）
        独立再校验一次，判据相同
        —— 与 ALC 的 fn_sideGuard 同源理由：只做一处校验的失效方式是静默的
   ↓
第三层  交付前静态验证（tools/sqf_syntax_check.py）
        把表达式塞进最小 SQF 文件，用真实解析器检查语法
```

第三层尤其重要：它把"表达式写错"这类问题从**游戏内运行时**提前到**本机构建时**。
`compile` 失败在游戏里只是一行日志，在本机是一次可断言的失败。

## 三、白名单是怎么来的

`whitelist_from_library()` 从命令库生成，默认只收**引擎命令**（不含函数库），
并排除：

- **符号运算符别名**：命令库里有形如 `a_greater_b`、`a_or_b` 的键名，它们是
  中置运算符在库中的表示，**不是可调用的命令**。放进白名单会生成
  `_p0 a_greater_b _p1` 这种不存在的语法（实测被抓出）。
- **禁区成员**：`execVM` / `compile` / `callExtension` / `remoteExec` /
  `loadFile` 等，见 `DENY_NAMES`。

当前规模约 2546 条。

## 四、实测数据：语法通过率

批量验证方法：对命令库里"白名单内、含参数、参数不超过 3 个"的引擎命令，
按签名生成表达式，送去真实解析器检查语法。

| 阶段 | 通过率 | 说明 |
|---|---|---|
| 初版（单一"位置参数"模板） | **75.3%** | 148 中 113 |
| 加入符号别名过滤 | — | 排除了一批不是命令的键名 |
| 改按**签名形态**选模板 | **98.7%** | 150 中 148 |

失败样本揭示的真实原因（都不是"语法无法生成"）：

```
_p0 a_greater_b _p1        ← 符号运算符别名（已过滤）
_p0 actionKeysNames _p1 _p2 ← 应为数组形态 [_p1, _p2]（已按签名修正）
_p0 addResources [_p1, _p2] ← 剩余：命令库签名本身有缺陷
_p0 addTeamMember _p1       ← 剩余：同上
```

**结论**：剩下约 1.3% 的失败是**命令库签名数据缺陷**，不是方案缺陷。
这正是第三层静态验证的价值——它把这类缺陷从"上机后才发现"变成"构建时列出"。

## 五、残余风险（如实列出）

1. **参数语义错误仍然可能**：白名单保证了"命令合法"，但不保证"参数组合有意义"
   （例如把玩家对象传给只接受 AI 的对象参数）。这类风险在静态分发里同样存在，
   不是动态方案特有的。
2. **命令库签名缺陷会导致表达式语义错**（顺序反了、形态不对）。第三层验证只
   覆盖语法，不覆盖语义。缓解：把静态验证失败的条目回报给命令库，并在
   `cmd_info` 输出里标注可疑签名。
3. **仍未上机验证**：本机验证覆盖到"语法正确"，未覆盖"引擎运行时行为"。
4. **`compile` 的性能开销**未实测。计划在 SQF 侧做编译缓存（按表达式文本缓存），
   P1 上机时一并测量。

## 六、此方案的边界

- 它**不**放开禁区：`execVM`/`callExtension`/`remoteExec`/`loadFile` 等依然永久拒绝；
- 它**不**允许调用方下发任意文本：必须通过表达式生成器 + 校验器；
- 它**不**替代静态分发：`tools/gen_dispatch.py` 生成的 `switch` 分发仍在，
  两者共用同一份白名单与签名知识，避免"两套实现各自漂移"。
